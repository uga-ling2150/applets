## Online classroom collection and GitHub teacher access

Students open a room link/code without an account. Teachers use the “Sign in with GitHub” button, then create activities, view submitted counts, export CSV/JSON and release anonymous comparisons. No separate course password is created. Public GitHub source contains no student submissions.

Authorized GitHub IDs are set in `wrangler.jsonc`: Ryan (`kayaulai`, 43101723) and the developer/reviewer (`yan2li3`, 316212992). Authorization compares immutable IDs, not usernames. Each new room belongs to the creating teacher; the dashboard lists only that teacher's unexpired rooms. Legacy rooms without an owner remain accessible only to approved teachers who know the old room code; their old bearer links alone no longer authorize access. Legacy rooms are not automatically listed because the original service had no account index.

The OAuth application is owned by `yan2li3`. It requests public identity only, without repository access. Its callback is `https://ling2150-7a-classroom.ling2150-query-rewrite.workers.dev/api/teacher/callback`. The client ID is public configuration; store `GITHUB_CLIENT_SECRET` with Wrangler secrets, never in source or HTML. GitHub user access tokens are used to fetch identity and are not stored. Login uses PKCE, a browser-bound state cookie, a single-use 60-second handoff and an eight-hour server-side session. The frontend holds its opaque session token in sessionStorage; sign-out revokes the session. The browser never receives the application secret. GitHub's own consent and reauthentication screens remain under GitHub's control.

Configure teacher IDs and client ID, run `wrangler secret put GITHUB_CLIENT_SECRET --config services/backchannel-locations/wrangler.jsonc`, then `wrangler deploy --config services/backchannel-locations/wrangler.jsonc`. Changing the owning Cloudflare account requires deploying there and updating the frontend API origin and OAuth callback. Removing a teacher ID blocks new sign-ins; revoke existing sessions as well for immediate removal.

Limits: 60 browser participants/room; 300 marks each; 30-day expiry; 100 room creations/day. Anonymous browser keys identify a participant within one activity; each completed attempt is immutable, and retries of the same attempt are idempotent. The class comparison uses the first completed attempt per participant. Switching browsers or clearing storage can create a second participant, so this is a discussion tool rather than attendance verification. Names, emails, voices and reflections are not collected by the app. The host processes ordinary network requests. Only a teacher release makes the comparison readable by room-code holders. The free hosting account has shared quotas; no paid upgrade is enabled.

## Anonymous attempt history

Each activity assigns a random browser participant, with up to 20 separately identified attempts. Refresh resumes the saved unfinished attempt; an explicit new attempt creates a separate record. Teacher-only history includes incomplete/discarded/completed attempts, task actions, client-reported UTC times and server receipt/submission UTC times. CSV downloads separate attempts from event history. Public comparisons expose neither action histories nor submission timestamps. Receipts use activity code, participant number and attempt number; they locate a record only when a student voluntarily supplies their receipt, not a verified identity. Clearing storage, private browsing or changing devices can create a new participant. Existing pre-history submissions have unknown timestamps and are shown as such.

Only allowlisted task events are stored: page open/reload/leave, start/pause/resume, marker/undo/discard, completion/retry, transcript/comparison views, practice start/end and audio waiting/errors. No free-text content, keystrokes, student names, emails, IPs or fingerprints are written to classroom records. Hosting processes network requests as usual. Events use a persistent local outbox and bounded batches (40); retries deduplicate event IDs. Abrupt browser termination, unavailable browser storage or clearing unsynced data can lose events, so this is not a guaranteed exhaustive or tamper-proof audit. Limits are 1,000 events per attempt or participant-level stream, and 20,000 per activity. Records expire after 30 days.
